## 1. なぜ測り直したか

ヴォイニッチの台本（`drafts/voynich-manuscript.txt`）は `script_engine check` に合格していた。

`check` が測っていたのは「型から外れていないか」であって「見続けられるか」ではない。

## 3. 章の中で何をしているか（ピラミッド回 第5章「石はどう積んだか」の分解）

参考の章は事実を並べていない。同じ順番の手順を踏んでいる。

```
問い            石をどうやって積み上げたのか。
結論を先に      じつは、決まっていない。これも正しい。
なぜか          なぜ決まらないのか。理由は、意外なほど単純だ。
着地            つまり、いちばん知りたいものが、いちばん残らない。
候補と留保      候補はいくつもある。〜。ただし角で向きを変えなければならず〜
伏線            その話は後の章でする。
通説を言わせる  ここから、いつもの一言が出る。決まらないのは、人間の力では建てられないからだ。
反転            だが、並んでいる候補は、全部人力である。差があるのは、坂の形だけだ。
新しい証拠      そして2018年、その坂の実物が出た。場所はギザではない。
前提が崩れる    坂は緩くなければ使えない。そう思われていた前提が、ここで崩れた。
数字と断り      中央値で13.8年から20.6年。ただし、この数字には断りが三つ要る。ひとつ〜ふたつ〜みっつ〜
結論の範囲      つまり「答えが出た」ではない。「人力でも数字が合う」というところまでだ。
次への引き      石は、音で浮かせて運ばれた。そういう説が、いま語られている。
```

うちのヴォイニッチ第1章は、これに対して「測定は4点。1点目が1404年。2点目が1438年。3点目と4点目も範囲内」と
**字数を埋めるために列挙していた**。字数を要求されて事実が足りないと、こうなる。

## 4. 作り替えたもの

```
従来   資料 → 一気書き → style で採寸 → 全文書き直し（2回）
いま   資料 → 設計図（章ごとの手順をJSONで決める） → 塊ごとに執筆 → devices + style で監査 → 外れた章だけ直す
```

- `script_engine/plan.py`    設計図。章ごとに 結論／なぜ／出どころ／振り子（肯定→反転→留保）／証拠／数字と断り／専門語の着地／語り手の判断／結論の範囲／引き。伏線を開く章と、題材より大きい主題（一般化）もここで決める。形が崩れていれば書かせ直す
- `script_engine/compose.py` 塊ごとに書く。冒頭 4.0% / 章 / 着地 11.5%。指摘は装置ごとに住んでいる塊へ配る（伏線→冒頭、回収→着地、率の不足→章）
- `script_engine/devices.py` 監査。上の表のレンジで指摘を出す。水増し（列挙の穴埋め・8文以内の言い直し）も拾う

### 語り手について守っていること

参考は「私も全部見た」「コメント欄を1700件読んだ」と行為を語る。それが信頼の演出になっている。
だがうちは生成なので、**行為を書けば捏造になる**。語り手が出るのは判断だけに限る。
「私は判断を保留する」「私はこの数字を疑っている」「私はこの説を採らない」。
`plan.validate` が「私は〜読んだ／数えた／測った」を落とす。

### 数字について

字数を要求すると、資料に無い数字が出る（`drafts/oparts_approved.txt` の「三内丸山遺跡の鉄剣」は
資料に無い）。設計図では数字ごとに「断り」を持たせ、`devices.unsourced_numbers` が
資料に無い数字を列挙して人に渡す。判定はしない。裏を取る工程は人間に残る。

## 5. 取れなかったもの

YouTube の「最も再生された場面」（heatmap）は、この環境からはどのクライアントでも取れなかった
（web/tv/mweb/ios は bot 判定、android_vr は heatmap を返さない）。
取れれば、参考動画のどの装置の直後で視聴が保たれたかを直接見られる。上の表は
「参考がやっていること」の実測であって、「効いていること」の実測ではない。
